# Generated Code

rotini generates **what is yours** and imports **what is ours**. Your CLI's shape — its command tree, typed inputs, and help text — is unique to your project, so it is written into your repo where you can read it, diff it, and own it. The machinery is an ordinary versioned import.

Nothing is injected at run time beyond two documented built-ins of the runtime itself: a hidden `__complete` entry point the generated shell-completion scripts call, and a default Ctrl-C/SIGTERM handler (turn it off with `WithoutSignalHandling`). Every generated line is in your repo, readable in a diff and yours to edit or delete.

## What lands where

The `.rotini.conf.*` file declares the code targets, one per `type`. All generated Go goes to one of them; the conf's `schemas` and `features` entries say where the JSON Schema files and any rendered help, man, markdown and completion files go.

| Target | Contents | Overwritten? |
|---|---|---|
| `main` | the binary entrypoint, carrying the `//go:generate` directive | **never** — create-once, because it holds your build metadata |
| `cmd` | the one generated file **plus** one editable handler stub per command | the generated file every pass; stubs are never overwritten, but are deleted when their command leaves the spec (see [Pruning](#pruning)) |
| `models` | **optional** — the typed structs, split into their own package so a handler package can import them without a cycle (see [configuration](/configuration)) | every pass |

There is no `runtime` target: the rotini runtime is a library you `go get`, not emitted code.

## The generated file

One file per CLI, marked `DO NOT EDIT`. Abridged here — the real file also carries the imports, every command's full definition (summaries included) and the page text for each enabled feature:

{{< code title="internal/cmd/todo/zz_rotini.go" language="golang" open="true" collapsible="false" copy="false" >}}
// Code generated by rotini; DO NOT EDIT.
package todo

// 1. The aggregate handler interface — the compiler checks you implement every command.
type ProgramHandlers interface {
	Todo() rotini.Handlers
	TodoAdd() rotini.Handlers
	TodoList() rotini.Handlers
}

// 2. The command tree, as data.
var definition = rotini.Definition{
	Name:    "todo",
	Handler: "Todo",
	Commands: []rotini.CommandDef{
		{Name: "add",
			Handler: "TodoAdd",
			Summary: "add a task",
			Flags: []rotini.FlagDef{
				{Name: "priority", Identifiers: []string{"-p", "--priority"}, Type: "string",
					Default: "normal", Enum: []string{"low", "normal", "high"}},
			},
			Arguments: []rotini.ArgDef{
				{Name: "title", Type: "string", Required: true,
					Constraints: rotini.Constraints{MinLength: 1}},
			},
		},
		// …
	},
}

// 3. The typed inputs — what Collect[T] decodes into. You never write these.
type TodoAddFlags struct {
	Priority string   `rotini:"priority"`
	Tag      []string `rotini:"tag"`
}

type TodoAddArguments struct {
	Title string `rotini:"title"`
}

type TodoAddInputs struct {
	Todo    TodoCommandInputs
	TodoAdd TodoAddCommandInputs
}

// 4. The descriptor the input binder reads (env prefix, config files).
var BindMeta = rotini.BindMeta{}

// 5. The constructor, and the rollup: the wiring and the ready-to-run Program.
func NewProgram(handlers ProgramHandlers) *rotini.Program {
	return rotini.NewProgram(definition, handlers).
		WithBindMeta(BindMeta).
		WithHelp(Help) // present when the help feature is enabled
}

type handlers struct{}

var Program = NewProgram(&handlers{})

// Handlers returns a fresh ProgramHandlers — what a test passes to NewProgram.
func Handlers() ProgramHandlers {
	return &handlers{}
}

func (*handlers) TodoAdd() rotini.Handlers {
	return &todoAddHandlers{} // the type in your stub, todo_add.go
}

// 6. One lookup function per enabled feature: Help, Man and Markdown by command path,
// Completion by shell name.
func Help(path ...string) (string, error) {
	switch strings.Join(path, " ") {
	case "":
		return HelpTodo, nil
	case "add":
		return HelpTodoAdd, nil
	// …
	default:
		return "", fmt.Errorf("no help for command %q", strings.Join(path, " "))
	}
}
{{< /code >}}

`NewProgram` takes the typed `ProgramHandlers`, so **a command without a handler is a compile error**, not a runtime surprise.

## Handler stubs

One per command, created once and then yours. rotini never overwrites a stub — regenerate as often as you like. The one exception is removal: when a command leaves the spec, its stub is deleted (see [Pruning](#pruning)).

Stubs and the generated types share **one package**, so a handler refers to its own input type unqualified:

{{< code title="internal/cmd/todo/todo_add.go" language="golang" open="true" collapsible="false" copy="true" >}}
func (*todoAddHandlers) Run(ctx context.Context, rtx *rotini.Context) {
	inputs, err := rotini.Collect[TodoAddInputs](rtx) // not somepkg.TodoAddInputs
	if err != nil {
		rtx.HaltWith(err)
		return
	}
	// …
}
{{< /code >}}

## Pruning

Files rotini generated that no longer map to a command are **removed** on each pass, and each removal is reported (`Note: pruned todo_version.go — its command is no longer in the spec`). That includes the command's handler stub, **even if you edited it**.

A stub is recognized by the line it is written with, `var _ rotini.Handlers = (…)`. A file without that line — a helper, a shared registry key, anything you wrote yourself — is never removed, and neither are `*_test.go` files or seeded templates. To keep a stub whose command you are removing, delete that line or list the file under the cmd target's `keep`.

## Derived outputs

Help pages, man pages, markdown reference pages and shell completion scripts are each a feature in the conf. `rotini init` turns help on so `--help` works from the first build; the other three are opt-in. Each has two independent knobs:

- **`embed`** — write the rendered content to a file and reference it with `//go:embed`, or (the default) inline it as a string literal so the generated `.go` is self-contained.
- **`template`** — seed an editable `*.tmpl` you can restyle, or (the default) render from rotini's built-in. A seeded template is written only when missing, so it becomes your file the moment it exists.

Because these are generated at codegen rather than produced by running your binary, they land in your diff and can be reviewed like any other change.
